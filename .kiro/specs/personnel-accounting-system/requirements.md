# Requirements Document

## Introduction

Система учёта личного состава — веб-приложение с Android-клиентом для воинских подразделений (МВД и аналогичных организаций). Система позволяет руководителям вести расход личного состава дважды в сутки, объявлять тревогу с отслеживанием откликов сотрудников, а администраторам — управлять личным составом, справочниками и учётными записями. Сотрудники получают push-уведомления о тревоге на Android-устройства и подтверждают получение сигнала.

## Glossary

- **System** — система учёта личного состава в целом (бэкенд + веб-фронтенд + Android-приложение)
- **Backend** — серверная часть системы (REST API на Node.js/Express/TypeScript + PostgreSQL)
- **Web_App** — веб-приложение (React SPA, Vite) для администраторов и руководителей
- **Android_App** — мобильное приложение для сотрудников (Kotlin, Retrofit, Room, WorkManager)
- **Admin** — пользователь с ролью «администратор», управляет личным составом, справочниками и учётными записями
- **Commander** — пользователь с ролью «руководитель», ведёт расход и объявляет тревогу
- **Employee** — пользователь с ролью «сотрудник», получает push-уведомления через Android-приложение
- **Raskhod** — расход личного состава: документ, фиксирующий статус каждого сотрудника подразделения на конкретное время (09:00 или 21:00) и дату
- **Alert** — сигнал тревоги, инициированный руководителем
- **FCM** — Firebase Cloud Messaging, сервис push-уведомлений для Android
- **JWT** — JSON Web Token, механизм авторизации (access + refresh)
- **Status** — статус присутствия сотрудника: «налицо», «болен», «наряд», «командировка», «отпуск», «незаконно отсутствует»

## Requirements

### Requirement 1: Схема базы данных

**User Story:** Как разработчик, я хочу иметь нормализованную схему БД, чтобы все данные системы хранились согласованно.

#### Acceptance Criteria

1. THE System SHALL хранить данные в СУБД PostgreSQL.
2. THE System SHALL содержать таблицу `roles` с полями: `id`, `name` (значения: «user», «admin», «commander»).
3. THE System SHALL содержать таблицу `users` с полями: `id`, `login`, `password_hash`, `role_id` (FK → `roles`), `unit_id` (FK → `units`, nullable).
4. THE System SHALL содержать таблицу `user_statuses` с полями: `id`, `name` (значения: «налицо», «болен», «наряд», «командировка», «отпуск», «незаконно отсутствует»).
5. THE System SHALL содержать справочные таблицы `positions` (должности), `ranks` (звания), `units` (подразделения), каждая с полями `id` и `name`.
6. THE System SHALL содержать таблицу `employees` с полями: `id`, `user_id` (FK → `users`, nullable, ON DELETE SET NULL), `last_name`, `first_name`, `middle_name`, `position_id`, `rank_id`, `birth_date`, `unit_id`, `phone_number`, `fcm_token`.
7. THE System SHALL содержать таблицу `audit_log` с полями: `id`, `user_id`, `date_time_in`, `date_time_out`.
8. THE System SHALL содержать таблицу `raskhod` с полями: `id`, `raskhod_time` (09:00 или 21:00), `raskhod_date`, `created_by_user_id`, `unit_id`, UNIQUE(raskhod_date, raskhod_time, unit_id).
9. THE System SHALL содержать таблицу `raskhod_entries` с полями: `id`, `raskhod_id`, `employee_id`, `status_id`.
10. THE System SHALL содержать таблицу `alerts` с полями: `id`, `created_by_user_id`, `created_at`, `unit_id`.
11. THE System SHALL содержать таблицу `alert_responses` с полями: `id`, `alert_id`, `employee_id`, `responded_at`, UNIQUE(alert_id, employee_id).
12. THE System SHALL содержать таблицу `refresh_tokens` с полями: `id`, `user_id` (FK → `users`, ON DELETE CASCADE), `token`, `expires_at`, `created_at`.

### Requirement 2: Аутентификация и авторизация

**User Story:** Как пользователь системы, я хочу входить по логину и паролю, чтобы получить доступ к функциям своей роли.

#### Acceptance Criteria

1. WHEN пользователь отправляет корректные `login` и `password`, THE Backend SHALL вернуть JWT access-токен и refresh-токен, а также роль пользователя.
2. IF пользователь отправляет некорректные `login` или `password`, THEN THE Backend SHALL вернуть HTTP 401 с описанием ошибки.
3. WHILE JWT access-токен действителен, THE Backend SHALL разрешать доступ к защищённым эндпоинтам без повторной аутентификации.
4. WHEN JWT access-токен истёк и пользователь предоставляет действующий refresh-токен, THE Backend SHALL выдать новую пару токенов (rotation — старый refresh-токен удаляется).
5. THE Backend SHALL хранить пароли исключительно в виде хэша (bcrypt, cost factor ≥ 10).
6. THE Backend SHALL фиксировать время входа (`date_time_in`) и выхода (`date_time_out`) каждого пользователя в таблице `audit_log`.
7. THE Backend SHALL определять `unit_id` пользователя через COALESCE(employees.unit_id, users.unit_id), чтобы командир работал и без записи в таблице employees.

### Requirement 3: Управление личным составом и справочниками (Admin)

**User Story:** Как администратор, я хочу управлять личным составом, учётными записями и справочниками, чтобы поддерживать актуальность данных системы.

#### Acceptance Criteria

1. THE Web_App SHALL предоставлять Admin страницу «Личный состав» с двухшаговым интерфейсом: выбор подразделения → список сотрудников с возможностью добавления, редактирования и удаления.
2. THE Web_App SHALL позволять Admin при добавлении/редактировании сотрудника указать ФИО, звание, должность, телефон и опционально создать или привязать учётную запись (с указанием роли и логина/пароля).
3. THE Web_App SHALL предоставлять Admin отдельный раздел «Учётные записи» для прямого управления аккаунтами (включая создание учётных записей администраторов).
4. THE Web_App SHALL предоставлять Admin интерфейс CRUD для справочников: `positions`, `ranks`, `units`, `user_statuses`.
5. WHEN Admin создаёт нового пользователя с уже существующим `login`, THE Backend SHALL вернуть HTTP 409 с сообщением о конфликте.
6. WHEN Admin удаляет справочную запись, на которую есть активные ссылки, THE Backend SHALL вернуть HTTP 409 и не выполнять удаление.
7. THE Backend SHALL возвращать постраничные списки сущностей с поддержкой параметров `page` и `page_size`.
8. THE Web_App SHALL предоставлять Admin раздел «Журнал входов» с историей сессий всех пользователей (логин, роль, время входа/выхода, длительность сессии).
9. THE Backend SHALL поддерживать фильтрацию сотрудников по подразделению (`?unit_id=X`).
10. THE Web_App SHALL предоставлять поиск по ФИО в списке сотрудников подразделения.

### Requirement 4: Ведение расхода личного состава (Commander)

**User Story:** Как руководитель, я хочу заполнять расход личного состава дважды в сутки, чтобы фиксировать статус каждого сотрудника подразделения.

#### Acceptance Criteria

1. WHERE Commander имеет активную сессию, THE Web_App SHALL отображать форму расхода со списком подчинённых (без самого командира).
2. THE Web_App SHALL устанавливать статус «налицо» для каждого сотрудника по умолчанию при открытии формы расхода.
3. WHEN Commander выбирает статус сотрудника через чипы-кнопки, THE Web_App SHALL немедленно отразить изменение в форме без перезагрузки страницы.
4. THE Web_App SHALL предоставлять Commander выбор времени расхода: «09:00» или «21:00», и выбор даты.
5. WHEN Commander нажимает «Отправить», THE Backend SHALL сохранить запись в таблицах `raskhod` и `raskhod_entries` и вернуть HTTP 201.
6. IF Commander пытается отправить расход на дату и время, для которых запись уже существует, THEN THE Backend SHALL вернуть HTTP 409 с соответствующим сообщением.
7. THE Web_App SHALL отображать историю расходов в двухколоночном интерфейсе (список слева, детали справа) с группировкой по месяцам, поиском по дате и фильтром по времени (утренний/вечерний).
8. THE Web_App SHALL позволять Commander редактировать статусы сотрудников в ранее созданном расходе.
9. THE Web_App SHALL позволять Commander скачивать расход в формате DOCX (таблица с ФИО и статусами).
10. THE Web_App SHALL позволять Commander удалять записи расхода с подтверждением.

### Requirement 5: Объявление тревоги (Commander)

**User Story:** Как руководитель, я хочу объявлять тревогу одним нажатием кнопки, чтобы мгновенно оповестить всех сотрудников подразделения.

#### Acceptance Criteria

1. WHERE Commander имеет активную сессию, THE Web_App SHALL отображать кнопку «Объявить тревогу».
2. WHEN Commander нажимает кнопку «Объявить тревогу», THE Backend SHALL создать запись в таблице `alerts` и вернуть HTTP 201.
3. WHEN запись в `alerts` создана, THE Backend SHALL отправить FCM push-уведомление на все зарегистрированные Android-устройства сотрудников данного подразделения.
4. IF FCM возвращает ошибку доставки для конкретного устройства, THEN THE Backend SHALL зафиксировать ошибку в журнале и продолжить отправку остальным устройствам.
5. THE Web_App SHALL отображать Commander список сотрудников подразделения (без самого командира) с индикацией: «принял» / «не ответил» — обновляя данные через polling каждые 10 секунд.
6. THE Web_App SHALL отображать Commander время ответа каждого сотрудника, подтвердившего получение сигнала.
7. THE Web_App SHALL сохранять идентификатор активной тревоги в localStorage, чтобы состояние не терялось при перезагрузке страницы.
8. THE Web_App SHALL отображать историю всех прошлых тревог в двухпанельном интерфейсе с поиском по дате, фильтром по полноте отклика и детализацией откликов с поиском по ФИО.

### Requirement 6: Получение сигнала тревоги (Employee, Android)

**User Story:** Как сотрудник, я хочу получать push-уведомление о тревоге на телефон, чтобы своевременно реагировать на сигнал.

#### Acceptance Criteria

1. WHEN Android_App получает FCM push-уведомление о тревоге, THE Android_App SHALL воспроизвести звуковой сигнал (будильник) через foreground service и отобразить полноэкранную активность.
2. WHEN Android_App отображает экран тревоги, THE Android_App SHALL показать кнопку «Принял».
3. WHEN Employee нажимает кнопку «Принял», THE Android_App SHALL отправить запрос в Backend с идентификатором тревоги.
4. WHEN Backend получает подтверждение от Employee, THE Backend SHALL создать запись в таблице `alert_responses` и вернуть HTTP 201.
5. IF Android_App не имеет сетевого соединения в момент нажатия «Принял», THEN THE Android_App SHALL сохранить ответ в локальной Room БД и отправить его в Backend при восстановлении соединения через WorkManager.
6. THE Android_App SHALL регистрировать FCM-токен устройства в Backend при каждом входе пользователя в систему.
7. THE Android_App SHALL отображать на главном экране профиль сотрудника: ФИО, звание, должность, подразделение (загружается с Backend через `GET /api/employees/me`).

### Requirement 7: Безопасность и разграничение доступа

**User Story:** Как владелец системы, я хочу, чтобы каждая роль имела доступ только к своим функциям, чтобы исключить несанкционированные действия.

#### Acceptance Criteria

1. THE Backend SHALL ограничивать доступ к эндпоинтам расхода и тревоги только пользователями с ролью «commander».
2. THE Backend SHALL ограничивать доступ к административным эндпоинтам только пользователями с ролью «admin».
3. THE Backend SHALL ограничивать доступ к эндпоинту подтверждения тревоги только пользователями с ролью «user».
4. IF запрос к защищённому эндпоинту поступает без валидного JWT, THEN THE Backend SHALL вернуть HTTP 401.
5. IF пользователь с недостаточными правами обращается к эндпоинту, THEN THE Backend SHALL вернуть HTTP 403.
6. THE Backend SHALL валидировать все входящие данные и отклонять запросы с некорректным форматом, возвращая HTTP 400 с описанием ошибки.

---

### Requirement 8: Навигация и единообразие интерфейса

**User Story:** Как пользователь системы, я хочу иметь единообразную навигацию на всех страницах, чтобы быстро переключаться между разделами.

#### Acceptance Criteria

1. THE Web_App SHALL предоставлять Commander единую навигационную панель на всех страницах с кнопками: «Тревога», «История тревог», «Расход», «История расходов» и кнопкой «Выход».
2. THE Web_App SHALL подсвечивать активный раздел в навигации Commander.
3. THE Web_App SHALL предоставлять Admin боковое меню с разделами: «Личный состав», «Учётные записи», «Должности», «Звания», «Подразделения», «Статусы», «Журнал входов» и кнопкой «Выйти».
4. THE Web_App SHALL после логина администратора перенаправлять на `/admin/roster`, а после логина командира — на `/raskhod`.
